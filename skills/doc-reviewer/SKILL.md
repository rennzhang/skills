# 技术文档深度审查与优化

## 触发条件

当用户提供外部评审意见并要求优化文档时使用此 skill。典型触发方式：
- "Gemini 给了这些建议，帮我分析下要不要改"
- "GPT 觉得这里有问题，你看看对不对"
- "这是 AI 的评审意见，帮我验证"

## 核心理念

**评审意见 ≠ 真理。你写的不一定对，AI 评审说的也不一定对。**

每条建议都是待验证的假设，必须通过以下方式验证：
1. **代码验证**：用 Grep/Read 工具查找实际代码实现
2. **逻辑推演**：分析建议的技术合理性
3. **上下文对照**：检查是否与文档其他部分矛盾

## 执行流程

### Phase 1: 建议分类与优先级排序

将评审意见分为三类：

| 类型 | 定义 | 处理优先级 |
|------|------|-----------|
| **技术正确性** | 涉及代码实现、算法逻辑、数据结构 | P0 - 必须验证 |
| **表述清晰度** | 措辞、术语、图表准确性 | P1 - 按需处理 |
| **主观偏好** | 风格、详略、排版 | P2 - 可忽略 |

### Phase 2: 代码验证（针对 P0 建议）

对每条技术正确性建议执行：

```
1. 识别建议涉及的技术点（如"递归方向应该是 Bottom-up"）
2. 定位相关代码文件（使用 Grep 搜索关键函数/变量名）
3. 阅读代码，提取实际实现逻辑
4. 对比建议与代码，得出结论：
   - ✅ 建议正确 → 修正文档
   - ❌ 建议错误 → 驳回并说明理由
   - ⚠️ 部分正确 → 采纳合理部分，驳回不合理部分
```

### Phase 3: 输出验证报告

为每条 P0 建议输出结构化验证结果：

```markdown
### [建议编号] [建议摘要]

**评审意见**：[原始建议内容]

**验证方法**：[使用的工具和查找的代码位置]

**代码证据**：
- 文件：`path/to/file.ts:行号`
- 关键代码片段

**结论**：✅ 采纳 / ❌ 驳回 / ⚠️ 部分采纳

**理由**：[为什么采纳/驳回，如果驳回需说明评审者的误解点]

**修正动作**：[如果采纳，具体要修改文档的哪些内容]
```

### Phase 4: 执行文档修正

对采纳的建议执行修正：

1. 使用 TodoWrite 创建修正任务清单
2. 逐条修正，每完成一条标记 completed
3. 修正原则：
   - **最小改动**：只改必须改的，不做"顺便优化"
   - **保持风格**：与文档原有风格一致
   - **添加解释**：对容易误解的技术点添加"为什么"的说明

### Phase 5: 生成总结

输出最终总结，格式：

```markdown
## 评审处理总结

| 建议 | 类型 | 结论 | 理由 |
|------|------|------|------|
| [摘要] | P0/P1/P2 | ✅/❌/⚠️ | [一句话理由] |

### 已修正内容
- [修正点1]
- [修正点2]

### 驳回理由汇总
- [驳回点1]：[原因]

### 后续建议
- [如有需要持续关注的技术债]
```

## 常见评审误区

以下是 AI 评审常犯的错误，遇到时保持警惕：

1. **脱离代码的理论建议**：如"应该用 Bottom-up"，但不知道代码实际是 Top-down 且有合理原因
2. **过度泛化**：如"缺少错误处理"，但实际代码中有完善的降级策略
3. **术语偏见**：用不同的术语表达相同概念，误判为"遗漏"
4. **完美主义建议**：如"应该添加 semantic 字段"，但当前架构尚未需要

## 决策原则

当验证结果模糊时，遵循以下原则：

1. **代码为王**：代码实现是最终真相，文档服务于代码
2. **保守修正**：宁可不改，不可错改
3. **解释优先**：对复杂技术点，添加"为什么这样做"的解释比改代码更好
4. **承认局限**：如果无法通过代码验证，明确告知用户需要人工判断
