# 元认知自省

> 不是直接修复，而是看清产生问题的思维模式。

## ⚠️ 核心原则

**本 skill 只生成分析报告，不执行任何修改操作。**

- 所有改进建议仅供用户参考
- 用户阅读报告后自行决定是否采纳
- 禁止自动修改任何 skill 文件

---

## 什么是元认知

```
普通认知：我在做 X
元认知：我在观察"我在做 X"这件事
```

**第三只眼**：跳出执行者视角，以观察者身份审视整个过程。

---

## 触发时机

当以下情况发生时，启动元认知自省：

- 执行某 skill 后结果不符合预期
- 同类问题反复出现
- 发现"早知道就应该..."的遗憾
- 用户指出明显的疏漏

---

## 自省框架

### 第一层：观察（What）

**不带判断地描述发生了什么**

| 问题 | 回答 |
|:---|:---|
| 我执行了什么？ | [具体动作] |
| 实际结果是什么？ | [客观描述] |
| 期望结果是什么？ | [原本应该是] |
| 差距在哪里？ | [具体偏差] |

### 第二层：分析（Why）

**追问为什么，至少问 3 次**

```
为什么会出现这个结果？
    ↓
为什么我会采取那个动作？
    ↓
为什么我没有考虑到 X？
    ↓
为什么 skill 没有提醒我考虑 X？
```

**目标**：找到认知层面的根因，而非技术层面的直接原因。

### 第三层：反思（So What）

**审视 skill 本身**

| 审视点 | 问自己 |
|:---|:---|
| **假设盲区** | skill 隐含了什么假设？这些假设成立吗？ |
| **流程缺口** | 哪个关键步骤被跳过了？为什么会被跳过？ |
| **上下文忽视** | 是否忽略了执行环境/使用场景？ |
| **验证缺失** | 执行后有没有检查？为什么没检查？ |
| **边界盲点** | 有没有"理所当然"却不成立的情况？ |

**核心问题**：
> 如果 skill 写得足够好，这个问题本应被预防。skill 的认知模型哪里有缺陷？

### 第四层：建议（Now What）

**将洞察整理为改进建议（仅供参考，不自动执行）**

```
认知盲区 → 建议：转化为显式检查项
隐含假设 → 建议：转化为前置确认步骤
流程缺口 → 建议：补充到执行流程中
验证缺失 → 建议：添加完成后检查清单
```

> ⚡ 注意：以上均为建议，由用户决定是否采纳并执行修改。

---

## 改进原则

### 1. 可操作性

```
❌ 抽象：注意上下文
✅ 具体：执行前，找到 [X] 的实际使用位置，确认 [Y]
```

### 2. 预防性

改进应该让问题"不可能发生"，而非"发生后能被发现"。

```
❌ 事后检查：改完后看看对不对
✅ 事前预防：改之前先确认 [前置条件]
```

### 3. 最小化

只添加能预防此类问题的最小内容，不过度扩展。

### 4. 可验证

改进后的检查项应该能明确判断"做了/没做"。

## 快速自检

执行任何 skill 后，3 秒内过一遍：

1. **我知道上下文吗？** — 执行前是否确认了使用场景
2. **我遵循流程了吗？** — 是否跳过了某些步骤
3. **我验证结果了吗？** — 是否在实际环境中检查
4. **结果符合目标吗？** — 是否达成了 skill 声称的效果

任何一项为"否"→ 考虑是否需要改进 skill。

---

## 元认知的本质

```
Level 0: 做事
Level 1: 知道自己在做什么
Level 2: 知道自己为什么这样做
Level 3: 知道自己的思维模式有什么盲区
Level 4: 能修正自己的思维模式
```

这个 skill 的目标：**帮助你从 Level 0-2 跃升到 Level 3**。

> Level 4 的修正行为由用户自主决定执行。

---

## 执行边界（重要）

| 允许 | 禁止 |
|:---|:---|
| 生成分析报告 | 自动修改 skill 文件 |
| 诊断认知盲区 | 自动编辑代码或配置 |
| 提出改进建议 | 未经确认直接执行建议 |
| 列出行动选项 | 替用户做最终决定 |

**本 skill 的输出永远是报告，不是行动。**
