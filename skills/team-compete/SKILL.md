# 竞标式多团队方案评审

## 触发条件

当用户需要多套独立方案进行对比评审时使用。典型触发方式：
- "开三个团队各出一套方案"
- "用竞标模式评审这个设计"
- "多角度分析这个方案的调整方向"

## 核心理念

**独立思考 > 群体趋同。三个团队必须有思维差异化，否则竞标无意义。**

## 执行流程

### Phase 0: 理解挑战

1. 确认用户的评审主题和目标
2. 收集参考材料（现有文档、约束条件、用户偏好）
3. 确认评分维度（使用默认维度或用户自定义），参考 `references/scoring-criteria.md`
4. **确定会话命名空间**（session-name）：基于评审主题生成简短英文标识（如 `nav-redesign`、`auth-architecture`），用户可自定义覆盖
5. 将所有上下文整理为 `team-brief`——三个团队共享的输入，保存到 `.context/team-compete/{session-name}/team-brief.md`

### Phase 1: 并行出方案

使用 Task 工具并行启动 **3 个 Agent**（subagent_type: general-purpose），每个 Agent 模拟一个完整团队。

#### 团队差异化定位（必须遵守）

| 团队 | 思维风格 | PM 侧重 | UX 侧重 | Architect 侧重 |
|------|---------|---------|---------|---------------|
| Team 1 | **务实稳健** | 最小可行方案、风险控制 | 可用性优先、成熟交互模式 | 现有技术栈、渐进改造 |
| Team 2 | **用户体验极致** | 情感共鸣、用户故事驱动 | 创新交互、感官设计 | 为体验让步的技术选型 |
| Team 3 | **极简颠覆** | 砍功能、做减法、反常识 | 最少元素最大效果 | 最轻技术方案、挑战假设 |

#### 每个 Team Agent 的 Prompt 模板

```
你是一个由 PM + UX + Architect 组成的产品设计团队。

## 你的团队风格
{team_style_description}

## 挑战背景
{team_brief}

## 输出要求

以三个角色的视角依次思考，然后合并为一份完整方案：

### 1. 核心理念（一句话）
用一句话概括你们的方案核心。

### 2. 方案详述
按挑战涉及的每个维度展开，必须包含：
- 具体设计决策（不是方向性口号）
- 为什么这样选（与团队风格一致的理由）
- 预期用户体验（用户会看到/感受到什么）

### 3. 亮点自评（2-3 条）
你们方案最强的地方。

### 4. 已知风险（1-2 条）
诚实承认你们方案的薄弱环节。

### 5. 与其他可能方案的差异
假设其他团队可能采取的路线，说明你们为什么没选那条路。

## 输出路径
将方案写入：{output_file_path}
```

每个 Team Agent 的输出保存到命名空间目录下：
- `.context/team-compete/{session-name}/drafts/team-1.md`
- `.context/team-compete/{session-name}/drafts/team-2.md`
- `.context/team-compete/{session-name}/drafts/team-3.md`

### Phase 2: 收集结果

读取三份方案文件，确认三个团队确实产出了差异化方案。

如果发现两个团队方案高度雷同（核心理念相似度 > 70%），标记为 `convergence warning` 并在评审中说明。

### Phase 3: 专家评审

使用 Task 工具启动 **1 个独立评审 Agent**（subagent_type: general-purpose），确保评审上下文与出方案过程完全隔离，消除认知锚定效应。

#### 评审 Agent 的 Prompt 模板

```
你是一个独立的专家评审团，需要对三个团队的竞标方案进行公正评审并合并最终方案。

## 评审背景
{team_brief 内容}

## 评分维度与标准
{scoring-criteria 内容}

## 待评方案
请阅读以下三份方案文件：
- {session_path}/drafts/team-1.md
- {session_path}/drafts/team-2.md
- {session_path}/drafts/team-3.md

## 评审输出要求

### Part 1: 评审报告
输出到 {session_path}/drafts/review-report.md，包含：

#### 1. 逐维度打分
同一维度下三个团队横向对比，确保尺度一致。每个维度 1-10 分（整数），产出加权总分。

#### 2. 亮点与缺陷分析
为每个团队写出：
- 亮点（2 条）：具体到可以直接采纳的设计决策
- 缺陷（1-2 条）：具体的问题，不是泛泛的"不够好"

#### 3. 胜出团队
选出加权总分最高的团队作为基础方案，明确说明胜出理由。

#### 4. 从其他团队采纳的补充项
从非胜出团队中提取值得采纳的具体设计点（如果没有，写"无"，不凑数），格式：

| 补充项 | 来源 | 采纳理由 |
|--------|------|---------|
| {具体设计决策} | Team N | {为什么它比胜出方案在这个点上更好} |

### Part 2: 最终合并方案
基于胜出团队方案 + 补充项，输出到 {session_path}/final.md，格式要求：
1. 开头包含评分总表（简洁表格）+ 胜出团队一句话理由 + 补充项表格
2. 正文中每个设计决策后标注来源 [from Team N]
3. 补充项明确标注 [补充 from Team N]
4. 如有冲突，说明取舍理由
```

### Phase 4: 整理与交付

1. 确认评审 Agent 已输出 `review-report.md` 和 `final.md`
2. **用通俗语言讲解最终方案本身**（用户关心的是"这道菜好不好吃"，不是"厨房里怎么炒的"）：
   - 一句话说清方案核心：这个方案到底在做什么、解决什么问题
   - 用户视角走一遍：用户会看到什么、感受到什么、操作流程是怎样的
   - 方案最打动人的 2-3 个亮点：为什么这个方案好，好在哪
   - 需要注意的地方：方案的已知局限或取舍（如有）
3. 附上竞标过程摘要供追溯（折叠展示，非重点）：
   - 三团队评分表（简洁表格）
   - 补充项采纳表（简洁表格）
4. 告知用户：
   - 完整方案见 `final.md`
   - 过程文件保存在 `drafts/` 目录可追溯

## 关键规则

1. **独立性**：三个 Team Agent 不能看到彼此的输出，通过并行启动保证
2. **评审隔离**：评审 Agent 独立启动，不继承出方案过程的上下文
3. **差异化强制**：如果三个团队的核心理念几乎相同，评审阶段必须标记并分析原因
4. **补充项不是客气**：如果非胜出团队没有值得采纳的点，就写"无"，不凑数
5. **用户自定义优先**：如果用户指定了评分维度、团队风格或 session-name，覆盖默认配置
6. **上下文传递**：team-brief 必须包含用户提供的所有参考材料和约束条件
7. **命名空间隔离**：同一项目多次使用 skill 时，不同 session 的文件互不干扰

## 输出目录结构

```
.context/team-compete/
└── {session-name}/              # 命名空间（如 nav-redesign）
    ├── final.md                 # 最终合并方案（唯一交付物）
    └── drafts/                  # 过程文件（可追溯）
        ├── team-brief.md        # 共享输入（挑战背景+参考材料+约束）
        ├── team-1.md            # Team 1 方案
        ├── team-2.md            # Team 2 方案
        ├── team-3.md            # Team 3 方案
        └── review-report.md     # 评审报告（评分+亮点缺陷+补充项）
```

### 多次使用示例

```
.context/team-compete/
├── nav-redesign/                # 第一次：导航重构
│   ├── final.md
│   └── drafts/...
├── auth-architecture/           # 第二次：认证架构选型
│   ├── final.md
│   └── drafts/...
└── onboarding-flow/             # 第三次：新手引导设计
    ├── final.md
    └── drafts/...
```
